Optimizing Constrained Decoding: Less Work, Fewer Boundaries, Better Overlap

A practical look at the algorithms and execution boundaries behind constrained generation—from dynamic candidate sets to surprising CUDA synchronization points.

Engineering note · October 30, 2026 · Design and profiling concepts

Scope of this article. All examples use an invented identifier-generation task and illustrative code. There are no proprietary workloads, production measurements, or validated speedup claims here. A public synthetic benchmark is planned separately.

1. The workload: thousands of tiny decisions

Constrained decoding restricts the next token that a language model may emit. Simple examples include JSON grammar enforcement and enumerated options; harder examples combine a grammar with dynamic per-request candidate sets and stateful exclusions.

Imagine generating a structured list of artificial identifiers. Each identifier contains several tokens, and each request provides a list of acceptable identifiers. After an identifier has been selected, it is no longer eligible in the current sequence. This is a generic example, not a description of any particular application.

At each decode step, we need to advance the grammar, restrict the current identifier prefix to candidates, apply exclusion rules, and mask invalid logits. An individual decision might inspect a handful of integers. Repeating that decision across every token and every active sequence is what makes it expensive.

There are at least three independent sources of cost: unnecessary algorithmic work, orchestration overhead from Python and temporary allocations, and serialization when host-side work waits for the GPU. Optimizing one does not automatically solve the others.

2. Profile the critical path, not just the mask function

Before choosing a faster data structure, distinguish wall-clock time from actual CPU execution. A long CPU span may be performing Python bookkeeping—or blocking on a CUDA runtime call while the GPU completes already-enqueued work.

Useful measurements include mask-planning latency, Python call counts, allocations, per-row candidate size, trie degree, CPU-to-GPU transfers, CUDA synchronization calls, GPU kernel execution, time per generated token, and end-to-end request latency. A CPU/GPU timeline is especially useful when an asynchronous inference backend is involved.

4. Candidate-driven trie traversal

A trie is a natural representation for multi-token identifiers. Given the prefix already emitted, the next-token mask is the set of outgoing edges that still lead to at least one valid candidate.

A common approach scans every child of the current trie node and tests whether that child's subtree contains an eligible identifier. This is reasonable for small branching factors, but inefficient if the node has many children while the candidate set is sparse.

Suppose the trie's leaves are numbered in depth-first order. Every node v has a contiguous descendant-leaf interval [lo[v], hi[v]). Store the candidate leaves as a sorted, deduplicated array. Rather than examining every child, we can locate which child contains each relevant candidate leaf and jump past other candidates belonging to that same child.

Consider the simplified algorithm below. It assumes sorted, unique candidate leaf IDs, contiguous child intervals, and a separate exclusion membership check. The production-quality details—such as avoiding slices and handling terminal states—are intentionally omitted.

def next_tokens(state, sorted_candidates, excluded, trie):
    result = []
    i = lower_bound(sorted_candidates, trie.lo[state])
    while i < len(sorted_candidates):
        leaf = sorted_candidates[i]
        if leaf >= trie.hi[state]:
            break
        child = trie.child_containing(state, leaf)
        end = lower_bound(sorted_candidates, trie.hi[child], start=i)
        if any(x not in excluded for x in sorted_candidates[i:end]):
            result.append(trie.edge_token[child])
        i = end
    return result

When candidate density is low, this can avoid scanning subtrees with no relevant candidates. It also removes a reason to construct a separate compact trie for every candidate set. But the win is conditional: for dense candidate sets or low-degree nodes, scanning all children may be simpler and just as fast. The right comparison is optimized child-driven versus optimized candidate-driven traversal in the same language and data layout, not merely Python versus C++.

4. Exclusions should be candidate-aware

Consider a large set of already-excluded leaves S and a small candidate set C. Any excluded leaf outside C cannot affect the legal next tokens for this step. The relevant excluded set is simply S ∩ C.

Instead of repeatedly rebuilding and sorting a global union of excluded leaves, compute only what the current candidates need. A sorted-array merge works well when input lengths are comparable; a smaller-array binary-search strategy may be better when they differ greatly. If exclusion rules have multiplicities, exemptions, or other semantics, those rules must be preserved before applying the intersection shortcut.

Optimization principle: Narrow the problem to the currently reachable candidates before optimizing the set operation.

5. Stateful native execution: reduce boundary crossings

After algorithmic simplification, the remaining cost may come from thousands of tiny Python calls, temporary arrays, object lookups, and transitions between Python and native code. Making a four-microsecond trie walk faster is of limited value if the surrounding glue costs much more.

One possible architecture is a persistent native engine that stores, for each active sequence, its grammar state, current trie position, candidate-set reference, and relevant exclusion state. Each decode step passes the new token and receives a compact description of valid token groups. Rows with genuinely equivalent constraint states may share a computation.

Keep high-frequency, branch-heavy state in contiguous native memory. Grouping must include every constraint that affects the answer.

The key is not “C++ is faster than Python” in isolation. It is do less work, preserve incremental state, avoid repeated allocation, and amortize the cross-language call. Native code adds build, portability, and correctness complexity, so moving only the fixed hot path is usually easier to maintain than porting every feature.

6. The surprising case: a tiny copy can cause a large wait

Constraint processing ultimately modifies model logits. Seemingly equivalent PyTorch expressions can take different runtime paths. In some environments, an advanced-index assignment using a Python scalar may materialize a CPU-side scalar tensor and perform a host-to-device transfer.

# Alternative APIs for filling selected rows:
logits[rows] = float("-inf")
logits.index_fill_(0, rows, float("-inf"))

These expressions are not universally identical in performance or every execution detail. Their behavior depends on PyTorch version, device placement, indexing form, and stream context. They should be checked using a profiler and correctness tests rather than assumed to be equivalent.

A possible trace is aten::to → aten::_to_copy → aten::copy_ → cudaStreamSynchronize. The crucial issue is not necessarily the bandwidth cost of a tiny host-to-device transfer: a CPU synchronization call can wait for earlier GPU work to finish. Removing that blocking behavior may restore host/GPU overlap.

Once planning is faster, the CPU arrives earlier and experiences more of the remaining GPU work as a wait. The bottleneck has moved even though the tensor assignment did not change.

For a fair comparison, use the same logits, indices, model workload, and stream configuration; verify output equivalence and inspect CPU runtime calls, kernel traces, and the true end-to-end latency.

8. Preserve legality while optimizing

Performance gains are meaningless if they change the set of legal tokens. Use a simple independent reference implementation and compare the optimized mask across random tries, empty and dense candidate sets, shared prefixes, terminal states, and exclusions. For a stateful engine, compare incremental transitions against replaying the complete prefix.

There are two distinct correctness claims: mask equivalence (two implementations produce identical valid-token decisions) and semantic correctness (completed outputs satisfy the intended constraints). The first does not prove the second if the constraint specification itself is incomplete.

9. Takeaways

Constrained decoding is a systems problem as much as a data-structure problem. The most compelling optimizations often come from eliminating repeated work, narrowing state to current candidates, batching small decisions behind a native boundary, and preserving asynchronous CPU/GPU execution.

There is no universally fastest implementation. Candidate density, trie shape, sequence state, and engine scheduling determine where the time goes. Measure the full critical path, keep an independent correctness oracle, and let the profiler decide which layer to optimize next.
