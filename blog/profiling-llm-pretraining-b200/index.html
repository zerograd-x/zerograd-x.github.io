Why Your B200s Might Be Waiting: Profiling LLM Pretraining Bottlenecks

A slow training step is not necessarily a slow GPU kernel. Here are four places I look before optimizing the biggest matmul.

November 12, 2026 · Engineering investigation

Scope of this note. The diagrams and numerical shape examples are illustrative, not captured traces. This is an explanation of engineering mechanisms, not a public benchmark or a claim of cumulative training speedup. Environment-specific performance numbers are intentionally omitted.

1. CPU throttling: when tokenization leaves GPUs waiting

One of the most confusing training symptoms is GPU idle time alongside modest average CPU utilization. Those signals are not contradictory. Tokenizers may create Rayon thread pools independently in every training worker; collectively, they can create more runnable threads than a container CPU quota can sustain.

Linux CFS bandwidth control tracks CPU consumption over scheduling periods. A burst of concurrent tokenizer work can consume the quota early, forcing otherwise inexpensive work to wait. The resulting pause can delay batch preparation or GPU work submission. Minute-average CPU utilization may hide those short stalls.

Figure 1 · Conceptual timeline — not a profiler capture

A tokenizer burst can cause quota throttling, which delays submission and creates GPU idle gaps. The widths are illustrative, not measured durations.

Rather than disabling all parallelism, one option is to cap tokenizer threads:

export RAYON_NUM_THREADS=2

The value is a tuning parameter, not a universal default. Too few threads can slow preprocessing; too many can provoke throttling. Compare CFS throttling counters, collate latency, and GPU idle intervals under a representative workload. The mechanism is credible only if those measurements move together.

Lesson: CPU scheduling can be on the GPU's critical path even when aggregate CPU utilization looks low.

2. Hidden synchronization in packed attention

Sequence packing avoids unnecessary padding by concatenating shorter sequences. Variable-length attention kernels use cumulative offsets to distinguish the original segments. Given lengths [3, 5, 2], the cumulative boundaries are [0, 3, 8, 10].

An avoidable implementation pattern reconstructs boundaries from GPU-resident position_ids inside the decoder, then converts a GPU-derived maximum length to a Python integer. Reading that value on the host—for example with .item()—can synchronize with outstanding GPU work. Repeating the operation across layers makes the interruption harder to ignore.

Figure 2 · Metadata flow — conceptual before / after

When the collator already knows segment lengths, it can produce int32 cumulative-boundary tensors and Python maximum-length scalars directly, avoiding a GPU-to-host scalar round trip.

The alternative is to have the CPU collator construct cu_seqlens_q and cu_seqlens_k as integer tensors and max_seqlen_q/max_seqlen_k as ordinary Python integers. Move the tensors with the batch; do not derive scalar metadata back from GPU outputs.

Correctness is the more subtle issue. Wrong boundaries can leak attention across packed examples. Test irregular lengths, singleton segments, padding edge cases, and numerical output/gradient equivalence against a reference implementation. A faster training step is not evidence of correct segment isolation.

Lesson: Some of the most expensive synchronization points hide inside metadata handling rather than the attention kernel itself.

3. Vocabulary GEMM alignment

The language-model head computes logits as Z = H Wᵀ, with hidden states H ∈ R^(N×d) and vocabulary weights W ∈ R^(V×d). Kernel performance depends on shapes, strides, dtypes, hardware and library choices—not just total FLOPs.

As an illustrative example, padding V = 100,003 to V' = 100,008 can make one dimension friendlier to particular tiled GEMM implementations. That is a hypothesis to test, not a guarantee that multiples of eight will always be faster.

Unused rows must never become prediction targets. Mask padded logits to negative infinity for the loss, preserve the original target indexing, and map gradients back to the real vocabulary. Verify both losses and gradients at acceptable numerical tolerance.

The optimization can trade additional weight copies or temporary storage for better GEMM efficiency. Profile the projection itself, the chosen kernels, temporary memory and total step time. A locally faster matmul may not be a globally better implementation.

Lesson: Tensor representation and GEMM shape are part of the system design; mathematical equivalence alone does not imply equal execution cost.

4. Regional compilation: reducing decoder overhead

Decoder blocks contain RMSNorm, rotary embeddings, activation functions, casts, residual additions and intermediate transformations in addition to large matrix multiplications. Eager execution may launch many small kernels. For a small model, launch overhead and extra memory traffic can become a material part of a step.

Regional compilation targets repeated decoder layers rather than the entire distributed training program. Compatible pointwise operations may be fused, while specialized attention kernels and large GEMMs can remain separate. The actual fusion is compiler- and shape-dependent.

# Conceptual only: actual integration must account for wrappers,
# checkpointing, parameter names and model architecture.
for i, layer in enumerate(model.layers):
    model.layers[i] = torch.compile(layer)

Compilation introduces warm-up and sometimes recompilation overhead. Always separate initial compilation cost from steady-state step latency and full-job wall-clock time. Validate checkpoint compatibility, training-loss behavior and gradients; numerical similarity is not bitwise identity.

Lesson: Reducing many tiny kernels can matter as much as optimizing a large one—but compilation has to earn back its startup cost.

5. Profile the whole critical path

A training step spans data preparation, host scheduling, device transfers, synchronization, forward/backward compute, optimizer work and possibly distributed communication. A speedup in one component only helps if that component was on the critical path.

My preferred approach is to establish a representative measurement window, inspect CPU throttling and GPU idle timelines, find avoidable sync calls, check GEMM shapes and kernel-launch patterns, then change one variable at a time. After each change, profile again: removing the current bottleneck may expose a different one.

These four investigations should not be interpreted as sequential optimizations of a single run. Different loss paths, packing settings and distributed configurations can change which bottleneck matters. The results of separate A/B experiments cannot be multiplied into a combined speedup.

6. Lessons and open questions

Average utilization can hide stalls. Seemingly harmless tensor metadata can force a CPU/GPU rendezvous. Mathematically equivalent shapes can select very different kernels. And compilation can shift the bottleneck back toward the CPU data pipeline.

The useful question is rarely “Which GPU operator is slowest?” It is “What prevents the next training step from making progress?”

There are interesting open problems here: how should tokenizer concurrency adapt to container quotas? Can packed-attention metadata be carried through the full training path without reconstructing it? When is vocabulary padding worth its memory cost? Once decoder kernels are fused, what becomes the next critical-path constraint?
