FlashAttention: from a data-movement problem, step by step to the solution

The attention formula is already perfectly clear. So why do we need FlashAttention at all?

This article follows a single question all the way down: in the end we only need the output — so why write a huge intermediate matrix into device memory just to read it back? Can we compute one block and use it immediately?

Every time we hit an obstacle, we first make it concrete with numbers, then introduce the math that removes it. The main text contains only prose, formulas, worked examples done by hand, and diagrams — no code and no commands. We start with a single sample, a single head, no mask and no dropout, full-sequence forward pass; edge cases and advanced material come at the end.

1The problem: why are attention's intermediate results worth optimizing?

1.1 First, what is the task?

For a single query, attention assigns weights to the corresponding values according to how relevant that query is to each key, and then aggregates the information. Handling many queries together, we write:

S=QK⊤d,P=softmax(S),O=PV.

Forget the derivation for a moment and just look at what gets passed between the three steps:

StepWhat it producesWho needs it next
Q against K, relevanceScore matrix SSoftmax
Scores turned into probabilitiesProbability matrix PThe multiplication with V
Weight V by the probabilitiesFinal output OLater network layers

Each row of Q, K and V is one query, key and value respectively; K⊤ is the transpose of K, and d is the length of a query/key vector. Softmax acts on each row of S separately.

The point

What we ultimately need is O. S and P are intermediate results produced only in order to get O.

1.2 How big are those intermediates?

Suppose there are 4,096 queries and each query looks at 4,096 keys. Then S and P each hold

4096×4096=16777216

elements. At 2 bytes per element, one matrix takes

40962×2÷10242=32MiB.

S and P together come to 64 MiB — and that is still only one head of one sample, and does not include Q, K, V or O. This is a capacity budget for explicitly storing two matrices; it is not the actual peak memory of every implementation, and certainly not a runtime estimate.

1.3 The problem is not only space — the data has to be moved

In one common unfused implementation:

  1. A matmul computes S and writes it into HBM, the GPU's large-capacity device memory.
  2. Softmax reads S back out, computes P, and writes P back into memory.
  3. A later matmul reads P out again, multiplies it with V, and produces O.

Time is not spent only on multiplies and adds — it is also spent reading and writing the data those operations need. A core goal of FlashAttention is to avoid shuttling the full attention intermediates back and forth between HBM and on-chip storage. FlashAttention paper §1–3

The real question

The scores still have to be computed. But do they have to be stored in full before we can move on to the next step?

2The intuitive approach: compute a block, use a block — why does softmax block us?

2.1 A natural idea

Each round, compute only a small block of scores; immediately turn them into weights, weight the corresponding V, and accumulate into the output. Once that block is done, reuse the same scratch space for the next one.

Then the small intermediates have a chance to stay in the GPU's on-chip storage, instead of writing full S and P out to device memory.

Obstacle

Having computed this block's scores does not mean this block's final probabilities are determined.

2.2 State the softmax formula in full

For a row of scores [s1,s2,…,sN], the probability at position j is

pj=esj∑k=1Nesk.

The numerator is that position's own exponential weight; the denominator is the total exponential weight of the whole row. ∑ simply means "add these terms up".

Real implementations normally use the max-subtracted, numerically stable form:

m=max(s1,s2,…,sN).
pj=esj−m∑k=1Nesk−m

The max is subtracted before exponentiating, and every score in the row subtracts the same max. This is mathematically equivalent to the basic definition; Section 4 explains why, and why it avoids overflow from large positive exponents. Stable softmax was not invented by FlashAttention. Online normalizer paper §2

For now, notice the dependency both forms share: the final probability needs whole-row information, not just the current token.

2.3 Four tokens make the obstacle visible

To keep the arithmetic doable by hand, let each value be a single number, and take the following exponential weights as given:

TokenExponential weight wj=esjValue vj
A210
B120
C430
D140

2, 1, 4, 1 are the weights after exponentiation — not raw scores, and not probabilities. These numbers are a teaching setup; we will not recompute them from Q/K dot products here.

Give the row's total weight a name, Z:

Z=∑jwj=2+1+4+1=8.

So the probabilities for the complete row are

[2/8,1/8,4/8,1/8].

They sum to 1. Z is not a separately chosen constant, and it is not the token count; Z = 8 is what you get by adding those four exponential weights.

2.4 Why can't the first block finish its own softmax?

Suppose we have read only A and B so far, and see the weights [2,1].

If the row contained nothing else, the probabilities would be [2/3,1/3]. But C and D follow with weights [4,1], so A and B should really end up as [2/8,1/8].

Same two scores — and the share they deserve changed, purely because more data comes later.

So we cannot take each block's locally-normalized probabilities and use them as whole-row probabilities. The stable form does not remove the dependency either: the first block knows neither the final maximum nor the final exponential sum.

To cut intermediate storage we want to compute as we read; but the final probabilities depend on data we have not read yet. What now?

3First solution: the final probabilities are unknown, but numerator and denominator can still accumulate

3.1 Which part has to wait, and which part can be computed now?

A's contribution to the final output is

2Z×10.

We do not know Z yet, so we cannot pin down the final contribution. But 2×10=20 can already be computed, because

2Z×10=(2×1Z)×10division rewritten as multiplication by the reciprocal=1Z×(2×10)commutativity and associativity of scalar multiplication=20Z.

Here Z>0, because the weights are all positive. Commutativity lets us swap scalar factors; associativity lets us move the parentheses.

Solution

What must wait is the final division — not the multiplications that come before it.

3.2 Why can every division be deferred to the end?

Rewrite each token the same way:

O=2×10Z+1×20Z+4×30Z+1×40Z.

Every term carries the same factor 1/Z, so by distributivity cx+cy=c(x+y):

O=2×10+1×20+4×30+1×40Z.

Name the numerator total U:

U=∑jwjvj,Z=∑jwj,O=UZ.

This is not a new definition of attention — it is an equivalent way of writing the same weighted average. In general:

∑jwjZvj=1Z∑jwjvj=∑jwjvj∑jwj.

The condition that matters is: for one query, all these terms share the same non-zero denominator.

3.3 Now we can tile

First block, A and B:

Z1=2+1=3,U1=2×10+1×20=40.

We do not treat 40/3 as an output. We keep two running numbers: 3 and 40.

The second block, C and D, brings

Z2=4+1=5,U2=4×30+1×40=160.

Fold the new contributions in:

ProgressAccumulated weight ZAccumulated weighted total U
after block 1340
after block 23+5=840+160=200

Everything read, divide once at the end:

O=2008=25.

This uses associativity of addition:

(a+b)+c=a+(b+c).

For example the numerator goes from 20+20+120+40 to (20+20)+(120+40) — only the grouping changed; nothing was dropped or double-counted.

3.4 Why can we throw away the first block's temporary weights?

A and B's influence on the final output is already folded into U and Z. Later data only adds new contributions; we never need to recall A's and B's individual weights in order to update those two totals.

Even when later data makes the final denominator larger, the earlier numerator contribution of 40 remains valid. We never divided by a local denominator too early, so there are no local probabilities to fix up.

Counterexample

What we must not do is keep only each block's own average. Block one gives 40/3, block two gives 160/5=32; averaging those directly gives

40/3+322=683≈22.67,

not 25. The two blocks carry total weights 3 and 5 — they were never entitled to half each. The correct weighting is

38⋅403+58⋅1605=25.

3.5 What role does commutativity actually play?

Commutativity of addition, a+b=b+a, additionally lets us reorder the summation — for instance handling C and D before A and B.

But what moves together is the pair of weight and value: 4×30 must not turn into 4×10 because a weight moved. For a fixed query, the set of visible tokens taking part must also stay the same.

So the three rules each have their own job:

  • Distributivity — pull out the common factor so the division can be deferred.
  • Associativity — accumulate many terms in groups.
  • Commutativity — reorder summands while keeping their pairing intact; sequential tiling does not itself require reordering.

That removes the obstacle "the final probabilities are unknown, so we cannot continue". But accumulating esj directly still has a numeric-range problem.

4A new problem: the exponentials are too large — why does subtracting the max not change the result?

4.1 The numbers can overflow long before the final division

The weights in our example are tiny, but real scores can be large. Computing e1000 directly in ordinary FP32/FP64, for instance, exceeds the representable range.

So "accumulate first, divide last" is mathematically sound, yet the machine may still fail at the exponentiation step.

What we need

Shrink the weights without changing the final output.

4.2 Try it: divide every weight by 4

Leave the values alone and turn the exponential weights into

[2,1,4,1]/4=[0.5,0.25,1,0.25].

The new total weight is

0.5+0.25+1+0.25=2.

The new weighted total is

0.5×10+0.25×20+1×30+0.25×40=50.

And the answer is still 50/2=25.

Why? Every summand was divided by 4, and distributivity guarantees the total is divided by 4 as well. Numerator and denominator shrank by the same factor:

200/48/4=2008.

It does not have to be 4. For any positive number c,

∑j(wj/c)vj∑j(wj/c)=U/cZ/c=UZ.
Conclusion

Common scaling does not change the ratios between the weights, and does not change the final probabilities.

4.3 If the exponential already overflowed, is dividing afterwards still in time?

No. So the adjustment has to happen before exponentiating.

The tool is the exponent rule:

esj−m=esjem.

For a score it reads "subtract the same m"; for an exponential weight it reads "divide by the same em". So we can compute esj−m directly, without ever forming the possibly-overflowing esj or em.

Expanding the stable formula from Section 2:

esj−m∑kesk−m=e−mesj∑ke−mesk=e−mesje−m∑kesk=esj∑kesk.

Step one is the exponent rule; step two pulls out the common factor by distributivity; step three cancels a common non-zero factor. This is an equivalence proof under real arithmetic; it does not require the machine to actually compute those enormous intermediate numbers.

4.4 Why choose the maximum score?

For a row of finite scores, choosing m=maxjsj gives

sj−m≤0,0<esj−m≤1.

Every new weight is at most 1, and at least one of them equals 1.

For example, with scores [1000,1001], subtract the maximum 1001 to get [−1,0], then exponentiate to get roughly [0.368,1]. The overflow from large positive exponents is gone. Floating point still rounds, and extremely small weights may underflow to 0; this is not a claim that all numerical error disappears.

Don't conflate these

The two "divisions" are not the same operation:

  • Dividing by Z normalizes weights into probabilities, which sum to 1.
  • Dividing by em moves the weights onto a smaller scale; their sum is not required to be 1.

4.5 Wasn't Z equal to 8? Why is the new denominator 2?

Because they count weights at different scales:

SymbolDefinitionValue in this example, once everything is processed
Ztotal of the raw exponential weights, ∑jesj8
ltotal of the max-subtracted weights, ∑jesj−m2
Utotal weighted result at raw scale, ∑jesjvj200
atotal weighted result at the same scaled level, ∑jesj−mvj50

The exponential grows with the score, so the largest score corresponds to this example's largest exponential weight, 4 — that is, em=4. Hence l=Z/4, a=U/4, and a/l=U/Z=25. The definition of Z did not change; we simply started accumulating the scaled quantities instead.

The next obstacle

When reading block by block, the first block does not know the row's overall maximum. If a larger score turns up later, what happens to the old l and a?

5A new obstacle: the maximum changed — what happens to the old accumulators?

5.1 The first block uses the maximum it has so far

To line up exactly with the weights [2,1,4,1], this row of scores is

[ln2,0,ln4,0].

ln2 denotes the number whose exponential is 2, i.e. eln2=2; likewise eln4=4 and e0=1.

The first block's scores are [ln2,0], so the current maximum is m=ln2. Subtracting m is the same as dividing the weights by em=2:

[2,1]/2=[1,0.5].

Now accumulate:

l=1+0.5=1.5,a=1×10+0.5×20=20.

Three things get remembered: the current maximum ln2, and the two accumulators at that scale, 1.5 and 20.

5.2 The second block arrives — why can't we simply add?

The second block's scores are [ln4,0], so the maximum rises to m′=ln4. The new common reference should be "raw weights divided by 4".

The second block therefore gets the new weights

[4,1]/4=[1,0.25].

Mixing those straight into the first block's [1,0.5] goes wrong:

TokenRaw weightScaled by its own block's maximum
A, from block 122/2=1
C, from block 244/4=1
What broke

C ought to be twice A, and now they are equal. Block one was divided by 2, block two by 4 — quantities on different scales cannot be merged directly.

5.3 The fix: move the old accumulators onto the "divide by 4" scale

Block one was effectively divided by 2; to make it effectively divided by 4, multiply by 1/2 once more:

x4=x2×12.

But we did not keep the individual old weights — only the totals. What now?

Multiply the totals by 1/2 as well. Distributivity guarantees that scaling a sum is the same as scaling each of its terms:

0.5(1×10+0.5×20)=(0.5×1)×10+(0.5×0.5)×20.

So

lold, rescaled=1.5×0.5=0.75,
aold, rescaled=20×0.5=10.
Solution

No need to go back and recompute block one, and we are not modifying the original V. We are only adjusting the weight scale that the old contributions live on.

5.4 With the scales unified, fold in the new block

Block two contributes

lnew=1+0.25=1.25,anew=1×30+0.25×40=40.

Add old and new:

l′=0.75+1.25=2,a′=10+40=50.

And the result is still O=50/2=25.

Numerator and denominator have to be adjusted together. Rescaling only l while leaving the old a at 20 would wrongly give (20+40)/2=30.

5.5 Where does the general rescale factor come from?

The old contributions have already been divided by em; we now want them to be effectively divided by em′, so they should be multiplied by

α=emem′=em−m′.

In this example α=eln2−ln4=2/4=0.5. In practice we exponentiate the difference directly, rather than forming two possibly huge exponentials and dividing them.

For any old score,

es−m′=e(s−m)+(m−m′)=es−mem−m′=αes−m.

Step one adds and subtracts the same m; step two uses ex+y=exey. Every old term shares the same α, so it factors out of the sum, and both the old l and the old a get multiplied by it.

So for each new block we do:

Online softmax update
m′=max(m,block max score),α=em−m′,l′=αl+∑blockesj−m′,a′=αa+∑blockesj−m′vj.

The first block is simply initialized with its own maximum; after that the update repeats, and a/l is computed only at the very end. If the maximum did not change then m′=m, so α=1 and the old scale needs no adjustment at all.

This is the online softmax we needed: maintain correct normalization statistics block by block, instead of obtaining each token's final probability up front. See Online normalizer §3 for the algorithm, and FlashAttention-2 §3.1 for the accumulate-then-normalize-once formulation.

6Back to the GPU: how does this math reduce data movement?

6.1 The two dataflows side by side

Reading top to bottom:

  • Left, normal attention is a representative unfused implementation; the red boxes and arrows highlight the full S and P being written to HBM and then read back.
  • Right, FlashAttention fixes one Q block and streams K/V in block by block. Inside the green frame, the current tile is computed, rescaled and accumulated; the dashed green arrow means "go do the next block".
  • Blue arrows are input and output traffic. They have not disappeared — this is not a picture of "FlashAttention never touches device memory".
  • On-chip compute means the compute units plus the registers, shared memory and other scratch right next to them — not a separate device.

The diagram uses the Q-block-outer, normalize-at-the-end forward organization used throughout this article, which is closer to FA2; it does not claim every version has the same loop order. Arrows are data dependencies — not byte counts, not timings, and not a claim that each is a single physical memory access. Training additionally saves a small per-row statistic for the backward pass, omitted here; see the appendix.

6.2 Why can three accumulators change how execution works?

For one query, once a K/V block has been processed, the influence of its temporary scores and weights on the output has already been absorbed into m, l and a. When the next block arrives, only that accumulated state is needed — none of the past temporary scores or weights have to be kept.

So we can:

  1. Read in the current Q block and current K/V block, and compute the current score tile.
  2. Update the per-row max, and rescale the old accumulators if needed.
  3. Compute the scaled weights, immediately weight the current V, and update l and a.
  4. Reuse the scratch space for the next block; when all blocks are done, this Q block's output is ready.
The point

We are not producing full S and P and then slicing them up — from the very start we only ever produce the tile we currently need.

6.3 Why is this not just a space saving, but potentially faster?

HBM has large capacity; on-chip storage has small capacity but feeds the compute units at much higher bandwidth. A full S or P usually will not fit in the on-chip working set — a well-chosen tile will.

FlashAttention fuses the operations belonging to one block of data, so a temporary result is consumed on-chip as soon as it is produced, cutting the movement of large intermediates across the memory hierarchy. That is the bridge between the mathematical "we never need to store the full P" and the hardware execution. FlashAttention §2–3, FlashAttention-2 §2–3

It still has to process every query-key pair that should participate; the dominant cost of dense attention still grows quadratically with sequence length. Different Q blocks may also re-read the same K/V. So:

Saving the intermediate matrices and moving less data does not mean every input is read exactly once, and it certainly does not mean attention became linear in cost.

No fixed speedup factor is claimed here. Real gains depend on shapes, precision, masking, hardware and implementation. For the full I/O budget see the advanced notes.

7From hand arithmetic to real matrices: vectors, many queries, and Q blocks

7.1 What if a value is not a single number?

Everything still holds. If A's value goes from 10 to [10,100], multiplying by the weight 0.5 gives [5,50]. Each coordinate is multiplied by the same weight, and each is accumulated separately.

A scalar still distributes over vector addition:

c(u+v)=cu+cv.

Extend the example's four values to

[10,100],[20,200],[30,300],[40,400].

At the final "raw weights ÷ 4" scale:

a=[50,500],l=2,o=a/l=[25,250].
Shapes

For one query, m and l are still one number each; a becomes a vector of the output dimension. Processing more keys never adds new coordinates to a — it only updates the accumulated values in the coordinates already there.

This is just the two-dimensional extension of the main scalar example; the advanced notes use a different pair of 2-D values with output [2,1.25] — do not mix the two.

7.2 Multiple queries do not share one denominator

The same key generally scores differently against different queries. So each query has its own maximum, its own weight total, and its own output accumulator vector.

For query r:

srj=qr⋅kjd,mr=maxjsrj,lr=∑jesrj−mr,ar=∑jesrj−mrvj.

Finally each gives or=ar/lr. The division divides every output coordinate of a row by that row's own lr — it is not one shared denominator for the whole block.

7.3 A Q block just handles a group of queries at once

Let the query/key length be d and the value length dv; they need not be equal.

ObjectFull shapeMeaning
Q, KN×dN query / key vectors
VN×dvN value vectors
S, P (logically)N×Nscore and probability of every query against every key
ON×dvoutput vector per query

Handling Br queries and Bc keys at a time makes the current score tile Br×Bc.

Which requires:

  • Br maxima m;
  • Br weight totals l;
  • one Br×dv output accumulator block a.

The Qi in the diagram is the i-th Q block, not a single query. Batching queries together makes matrix multiplication and K/V reuse practical; the per-row normalization math is unchanged. The scratch space in the loop depends on the tile size and never has to hold the full N×N matrix.

7.4 This is not "commutativity of matrix multiplication"

What we swapped earlier were scalar factors and summands. Matrix multiplication is not commutative in general. For example:

A=[1101],B=[1011].

Then

AB=[2111],BA=[1112].

The top-left entry alone already differs: for AB it is 1×1+1×1=2, for BA it is 1×1+0×0=1.

Matrix multiplication is associative when the dimensions line up, (AB)C=A(BC), and it distributes — but that does not let us reach across the non-linear softmax in the middle and turn attention into Q(K⊤V).

Don't misread it

What FlashAttention changes is how the computation is grouped, what state is accumulated, and what gets stored — not the roles of Q, K and V.

8A CPU comparison: matmul tiling vs. fusing the whole attention

8.1 Does the CPU also hit "compute waiting on data"?

Yes. The CPU also has a hierarchy of storage with different capacities and access costs: registers, the cache levels, main memory.

Suppose we compute

[1234][5678]=[19224350].

The top-left entry is 1×5+2×7 and the top-right is 1×6+2×8. Both outputs need the left matrix's first row [1,2].

Once a piece of data has made it into a register or cache, we want to finish as many computations that depend on it as we can while it is still there — for instance updating a small block of outputs at once, rather than coming back much later for another related output.

That is the starting point for CPU tiling. It does not reduce the number of multiplications; it reorders the computation to shorten the gap between reuses of the same data. FLAME GEMM optimization tutorial

8.2 What do blocking, packing and fusion each solve?

TechniqueProblem it facesWhat it does
Cache blockinga large working set will not stay resident in the nearer cachesarrange access and computation block by block, reusing the current data as much as possible
Register blockingrepeatedly loading and storing the same input or partial sum costs somethingupdate a small output block at a time so partial sums can stay in registers
Packingthe original layout can make micro-kernel access non-contiguous and awkwardrearrange the needed block into a layout better suited to the accesses that follow
Operator fusionone step's temporary output has to be handed to the next steporganize supported operations together to shorten the lifetime of the temporary

Packing itself costs data movement — it trades one reorganization for easier access afterwards, and is not unconditionally faster. These matmul optimizations can be worked through step by step in the FLAME blocking / packing tutorial.

8.3 Matmul is already tiled — so why do we still need an attention-level solution?

Because these are two different scopes:

  • Inside a single matmul: how do we compute QK⊤ efficiently?
  • Between the stages of attention: once the scores exist, must the full S and P still be stored before the next step can run?

Even if both QK⊤ and PV use excellent tiled matmuls, as long as a complete S and P must be handed between them, the intermediate matrices are still there.

And the original softmax obstacle does not disappear just because the matmul got faster: the current block still does not know the whole-row normalization.

Online softmax plus rescaling supply the mathematical conditions for stepping over that obstacle, letting a score tile feed the final output accumulation directly. This set of recurrences is not GPU-specific; a CPU can use it too. Different hardware just needs different tiling, layout, vectorization and threading.

8.4 CPU cache and GPU shared memory are not the same thing

ConcernTypical CPU approachGPU FlashAttention as described here

What is being compared here is roles and ideas, not a one-to-one hardware mapping. GPUs also have hardware-managed caches; and a CPU writing a temporary array does not mean every write immediately reaches DRAM, since later reads may hit in cache. So the logical arrows in the diagram must not be read as actual CPU main-memory traffic.

Attention-level optimized implementations do exist on CPU. The oneDNN documentation lists an optimized CPU SDPA inference path along with its shape, runtime and parallelism conditions; that does not mean any CPU, framework call or training path automatically uses the same implementation. oneDNN SDPA: implementation limitations

8.5 What is this comparison supposed to establish?

Not "CPU versus GPU, and by how much", and not "hand-written tiling beats optimized libraries". What we are comparing is:

CPU matmul tiling already embodies "bring it close, then use it several times"; FlashAttention additionally has to resolve softmax's whole-row dependency before that kind of reuse can be extended across the entire attention computation.

For a more detailed CPU working-set budget, cache caveats and experimental boundaries, see the advanced CPU notes. This article performs no CPU/GPU performance measurement and claims no speedup factor on that basis.

In one sentence:

FlashAttention replaces the full intermediate matrices with statistics that can be updated block by block, then maps that way of computing onto the GPU's memory hierarchy to reduce data movement.

"Mathematically equivalent" here means it yields the same attention under real arithmetic. Floating-point rounds, and changing summation order does not guarantee bit-for-bit identical results. For instance in float64, adding 1016 and −1016 first and then adding 1 can give 1; computing −1016+1 first, rounding, and then adding 1016 can give 0. That is finite precision at work, not a failure of associativity over the reals.

Appendix: without storing the probability matrix, how does backpropagation work?

Earlier we said a tile can be released once it has been used — meaning it does not need to be kept around for the sake of later blocks. But training needs the probabilities to compute gradients. So what happens?

Solution

Keep enough information to reconstruct them, and recompute block by block when needed. FA2, for example, keeps Q, K, V and O, plus a log-sum-exp statistic L for each query row; the backward pass also receives the output gradient from the following layer. L is a per-row statistic, not a probability matrix. FlashAttention-2 §3.1.2

Reusing the notation above, the per-row statistic can be written

L=m+lnl=ln(∑jesj).

That identity comes from Z=eml. In practice L is obtained from the stably-computed m and l, without ever forming the possibly-overflowing Z.

So when the backward pass recomputes some score, its probability is simply

pj=esj−L.

In our example L=ln4+ln2=ln8, and A's probability is recovered as eln2−ln8=2/8.

The backward pass recomputes scores block by block, recovers the probabilities, and uses them immediately for gradient accumulation — rather than rebuilding a whole P and storing it permanently. The cost is extra arithmetic; the benefit is not storing and re-reading an enormous intermediate matrix. On suitable hardware and at suitable problem sizes that trade is worth it, but it does not license the claim that recomputation is always faster.

This only explains why training is still possible; it does not work through the full gradient derivation. See the advanced backward-pass notes.
